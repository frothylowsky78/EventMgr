# App Store & Google Play readiness

Everything needed to take the Flutter app from source to a submittable iOS + Android build.
Most native platform files are generated by `flutter create` and aren't committed; this repo ships
the **config + ready-to-apply overlays** (`apps/mobile/store/`) and brand assets so the steps below
are mechanical.

## 0. Generate the native platform folders (once)
The repo holds `lib/`, assets, and config but not `ios/` / `android/` (they're machine-generated):
```bash
cd apps/mobile
flutter create --org com.example --project-name eventmgr_mobile .
flutter pub get
```

## 1. App identity
| | iOS | Android |
| --- | --- | --- |
| Display name | `CFBundleDisplayName` (see overlay) | `android:label` / `app_name` resource |
| Bundle / App ID | `com.example.eventmgr` (per-flavor scheme) | `com.example.eventmgr` + `.dev` / `.staging` suffix |
| Version | `version: 0.1.0+1` in `pubspec.yaml` drives both `CFBundleShortVersionString`/build and `versionName`/`versionCode` |

Per-environment flavors let dev/staging/prod install side by side and point at the matching CDK
stack — see `apps/mobile/store/android-build.gradle.snippet.kts` and §4 below.

## 2. Launcher icon & splash (assets committed)
Brand assets are generated from the event palette (`tools/gen_app_assets.mjs`) into
`apps/mobile/assets/icon/app_icon.png` and `assets/splash/splash_logo.png`. **Replace with the
client's final artwork before submission.** Then:
```bash
cd apps/mobile
dart run flutter_launcher_icons
dart run flutter_native_splash:create
```
Config lives in `pubspec.yaml` (`flutter_launcher_icons:` / `flutter_native_splash:`).

## 3. Permissions (overlays in apps/mobile/store/)
Apply after `flutter create`:
- **iOS** → merge `ios-Info.plist.additions.xml` into `ios/Runner/Info.plist`
  (camera, photo library, calendar usage strings; `LSApplicationQueriesSchemes`;
  `ITSAppUsesNonExemptEncryption=false`).
- **Android** → merge `AndroidManifest.additions.xml` into
  `android/app/src/main/AndroidManifest.xml` (INTERNET, CAMERA, READ_MEDIA_IMAGES,
  POST_NOTIFICATIONS, and the `<queries>` block for `url_launcher`).

Usage strings must be specific — vague text is a common App Store rejection.

## 4. Environment build config
Copy `apps/mobile/config/*.example.json` → `dev.json` / `staging.json` / `prod.json` (git-ignored),
fill from CDK stack outputs (`ApiUrl`, `UserPoolId`, `MobileClientId`, `Region`), then:
```bash
flutter run                            --dart-define-from-file=config/dev.json
flutter build appbundle --flavor prod   --dart-define-from-file=config/prod.json   # Play
flutter build ipa       --flavor prod   --dart-define-from-file=config/prod.json   # App Store
```

## 5. Signing
- **Android:** create an upload keystore; put path/passwords in `android/key.properties`
  (git-ignored, see `.gitignore`); reference it from the release `signingConfig`. Enrol in Play
  App Signing.
- **iOS:** App Store Connect app record + distribution certificate + provisioning profile
  (or automatic signing in Xcode). Archive via `flutter build ipa` then upload with Transporter
  or `xcrun altool`.

## 6. Push notifications (ties to the backend)
- **iOS (APNs):** add the Push Notifications capability; create an APNs auth key (.p8); register
  the device token and call `NotificationsRepository.registerDeviceToken('ios', token)`.
- **Android (FCM):** add `google-services.json`; `firebase_messaging` for the token.
- Wire the APNs/FCM credentials into SNS platform applications and deploy with
  `--context pushIosArn=… pushAndroidArn=…` (see `services/api/README.md`).

## 7. Store listing assets & metadata
- **Screenshots:** iPhone 6.7"/6.5"/5.5" + 12.9" iPad (if tablet); Android phone + 7"/10" tablet.
- **Icon:** 1024×1024 (no alpha) for App Store; 512×512 for Play.
- **Copy:** name, subtitle/short description, full description, keywords, support URL, marketing URL,
  privacy policy URL (required — the app collects personal data).
- **Category:** Events / Business. **Content rating:** complete Play questionnaire; App Store age 4+.

## 8. Privacy declarations (required — app handles personal data)
The app collects name, email, phone, photos, dietary/accessibility info, and travel details.
- **Apple Privacy Nutrition Labels:** declare Contact Info, User Content (photos), Identifiers,
  and Sensitive Info (dietary/accessibility) — linked to the user, used for app functionality, not
  tracking.
- **Google Play Data Safety:** same data types; data encrypted in transit (HTTPS) and at rest
  (DynamoDB/S3 SSE); users can request deletion (post-event archive/retention policy — see
  `docs/open-questions.md` #5).
- Show the photo-upload consent/terms before first upload (spec §4.14) — pending UI copy.

## 9. Pre-submission QA (spec §14)
Run the QA matrix on real devices: login (valid/invalid/disabled), agenda by day + detail +
calendar add, itinerary isolation + timezone, push delivery + deep link + history, yearbook
search/visibility, travel/transport per-attendee correctness, dining menus/dietary/seating,
photo upload→moderation→gallery, FAQ search/featured, offline (agenda/itinerary/travel/dining/
FAQ/help viewable; photo upload queues).

## 10. Production launch checklist (spec §18.15)
- [ ] Prod CDK stack deployed; Cognito prod pool; admin MFA enforced
- [ ] APNs + FCM configured; push tested on real iOS + Android devices
- [ ] App points at prod API (`config/prod.json`); deep links tested
- [ ] S3 buckets private; CloudFront (if used) configured; DynamoDB PITR on
- [ ] Test attendee accounts + admin accounts created
- [ ] Attendee / travel / dining imports tested in prod
- [ ] Photo upload + moderation tested; offline cache + calendar sync tested
- [ ] CloudWatch alarms configured; post-event export process tested
- [ ] App Store + Play listings complete with privacy declarations
- [ ] Final branded icon/splash swapped in; screenshots captured
